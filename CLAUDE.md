## What this is

A QR-code restaurant menu site + admin panel for "Aydın Döner" (Çorlu, Turkey), built with Next.js 16 (App Router), React 19, Prisma/SQLite, and Tailwind v4. UI copy and validation messages are in Turkish.

## Commands

```bash
npm run dev            # start dev server (Turbopack)
npm run build           # production build
npm run start            # run production build
npm run lint             # eslint (flat config, eslint.config.mjs)

npm run prisma:generate  # regenerate Prisma client after schema changes
npm run db:push          # push prisma/schema.prisma to the SQLite db (no migration files)
npm run db:seed          # run prisma/seed.ts (tsx)
npm run db:reset         # prisma migrate reset --force (drops + reseeds)
```

There is no test runner configured in this repo.

Env vars (see `.env.example`): `DATABASE_URL` (SQLite file path), `JWT_SECRET` (admin session signing), `ADMIN_EMAIL` / `ADMIN_PASSWORD` (used by the seed script).

## Architecture

### Route groups: public site vs admin panel

- `src/app/(public)/` — the public-facing menu (home, category pages, product pages, hakkımızda/iletişim). Wrapped by `src/app/(public)/layout.tsx`, which loads site settings + active categories server-side and passes them into `SiteProvider` (`src/components/public/site-provider.tsx`), a client context consumed via `useSite()`.
- `src/app/admin/` — the admin panel, split into two sibling route groups so login isn't nested inside its own auth guard (avoids a redirect loop):
  - `admin/(protected)/` — dashboard, categories, products, daily-menu, settings. `admin/(protected)/layout.tsx` calls `getSession()`, redirects to `/admin/login` if unauthenticated, then renders `AdminClientShell`.
  - `admin/(auth)/login/` — the login page (client component using `useActionState`); `admin/(auth)/layout.tsx` just sets metadata, no auth check.
  - `admin/page.tsx` — bare `/admin` redirects to `/admin/dashboard`.
- Layouts use Next 16 typed route props (`LayoutProps<"/">`) generated by the `next` TS plugin where the route is a single concrete path — don't hand-write ad hoc prop types for those. The two route-group layouts above type `children` manually (`{ children: ReactNode }`) since a route group isn't a single addressable path.

### Auth

Custom JWT session auth (no NextAuth/Clerk), cookie name `aydin_admin_session`. Protection is layered — UI routing alone is not enough, because Next.js Server Actions are invoked by action ID and are **not** confined by a path-based proxy matcher:
- `src/lib/auth.ts` — `createSessionToken`/`verifySessionToken` (via `jose`), `getSession()`, `requireAdmin()` (throws `redirect("/admin/login")` if no session), cookie get/set/clear.
- `admin/(protected)/layout.tsx` calls `getSession()` to gate the admin UI itself.
- `src/proxy.ts` (Next 16's renamed `middleware.ts` — see `node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md`) re-verifies the JWT at the edge for `/admin/:path*` and bounces `/admin/login` → `/admin/dashboard` when already authenticated. Must live under `src/` (alongside `src/app`), not at the repo root, or Next silently fails to register it.
- **Every mutating Server Action in `src/actions/*.ts` also calls `await requireAdmin()` as its first line** — this is the real enforcement boundary, since a POST carrying a valid `Next-Action` header can reach an action regardless of which page/path it's sent to. When adding a new mutating action, always add this call; don't rely on the admin layout or proxy alone.
- `src/actions/auth.ts` — `loginAction` (`useActionState`-style: `(prevState, formData) => state`) checks `AdminUser` via bcrypt, `logoutAction` clears the cookie. Neither needs `requireAdmin()` (login is the entry point; logout is harmless unauthenticated).

### Data flow: reads vs writes are split

- **Reads** live in `src/lib/data/*.ts` (e.g. `categories.ts`, `products.ts`, `home.ts`, `settings.ts`), called directly from server components/layouts via plain async functions on top of the shared `prisma` client (`src/lib/prisma.ts`, a standard globalThis-cached singleton).
- **Writes** live in `src/actions/*.ts` as `"use server"` Server Actions (`auth.ts`, `categories.ts`, `products.ts`, `dailyMenu.ts`, `settings.ts`). They start with `await requireAdmin()` (see Auth above), parse/validate `FormData` with Zod schemas from `src/lib/validations.ts`, hit Prisma directly, and call `revalidatePath(...)` on the affected admin/public routes instead of using router refresh.
- Product/logo image uploads (`uploadProductImageAction` in `src/actions/products.ts`, `uploadLogoAction` in `src/actions/settings.ts`) write files straight to `public/uploads/products/` and `public/uploads/logo/` via `fs.writeFileSync` — there is no cloud storage/CDN integration. This is distinct from `public/images/`, which holds optional static decorative assets (hero background, section accents) read via `src/lib/static-image.ts`'s `getStaticImage()`, which returns `null` if the file hasn't been provided yet so pages degrade gracefully instead of rendering a broken `<img>`.

### Prisma / SQLite

- Config is `prisma.config.ts` (new-style Prisma config, not a `package.json#prisma` block only — note `package.json` also still declares `"prisma": { "seed": ... }"` for the seed command).
- Schema (`prisma/schema.prisma`) has four models: `Category` → `Product` (1:many, `onDelete: Restrict`), `SiteSettings` (effectively a singleton row), `AdminUser`.
- Slugs (`Category.slug`, `Product.slug`) are generated with `toSlug()` (`src/lib/utils.ts`, `slugify` with Turkish locale), not by the DB.
- Use `db:push` for schema iteration in dev (no migrations directory is checked in); use `db:seed` to (re)populate `AdminUser`/sample data from `prisma/seed.ts`.

### Shared UI/util conventions

- `cn()` (`src/lib/utils.ts`) = `twMerge(clsx(...))`, used throughout instead of raw template-string classNames.
- Turkish-specific formatting helpers live alongside it: `formatPrice` (TRY via `Intl.NumberFormat`), `buildWhatsappLink`/`buildTelLink`/`buildMapsLink`.
- `src/components/ui/*` are hand-rolled primitives (button, dialog, input, select, switch, textarea, toast, badge) — not a generated shadcn/ui library, so check the existing component before assuming a prop API.
- `src/components/admin/*` and `src/components/public/*` are feature-scoped client components consumed by the respective route group.

### SEO / structured data

- Per-route `metadata`/`generateMetadata` exports live on each public page (home, `kategori/[slug]`, `iletisim`, `hakkimizda`); the root layout sets a title template (`%s | Aydın Döner`). `metadataBase` is intentionally **not** set yet (no production domain decided) — `src/lib/site-url.ts`'s `getSiteUrl()` resolves absolute URLs from `NEXT_PUBLIC_SITE_URL` when it exists and falls back to relative paths otherwise, so JSON-LD/breadcrumbs degrade gracefully until a domain is set.
- `src/components/public/restaurant-json-ld.tsx` (Restaurant schema, home page) and `breadcrumb-json-ld.tsx` (BreadcrumbList, category pages) render `<script type="application/ld+json">` tags sourced from the same `SiteSettings` row everything else uses — don't hardcode business info a second time.
- `src/app/opengraph-image.tsx` generates the social share image at request time via `next/og`'s `ImageResponse` (no static asset to maintain). `icon.png`/`apple-icon.png` are static files following Next's app-icon convention.
- `src/components/public/empty-state.tsx` is the single shared "nothing here yet" UI (used on the home page's per-category cards and the category page's no-products case) — reuse it rather than inlining another empty-state div.

### Home page: scroll-driven cinematic intro

- `src/app/(home)/` is its own route group (own layout, no site header/footer, Bebas Neue loaded only here). `(public)` keeps `gunun-menusu` and `iletisim`.
- `src/components/home/cinematic-home.tsx` (client) renders the scene sections + passes the server-rendered `HomeMenu`/`HomeContact` through as children. `src/lib/cinematic/engine.ts` (GSAP ScrollTrigger + Lenis + one fixed canvas) is **dynamically imported after `window.load`** so GSAP/Lenis never reach `/menu` or product pages.
- Frames live in `public/frames/{desktop,mobile}/sahne-N/0001.webp…` plus `public/frames/poster/sahne-N.webp` and `poster/menu.webp`. `src/lib/cinematic/scenes.json` is the single source for which video feeds which scene and how many frames each gets (read by both the engine and `scripts/extract-frames.sh`; regenerate frames after editing it). Desktop frames are up to 1920px wide (q80, never wider than the source). Mobile frames are a vertical 9:16 slice cut from the full source height (q86), used for portrait screens <=820px only, so each stored pixel is shown 1:1; the engine draws one real frame at a time (no blending, which ghosted fast motion). The mp4s in `kaynak-videolar/` are gitignored and never served. Budget per scene: desktop <=8 MB, mobile <=3.5 MB.
- Colour lives only in `src/app/globals.css` (`--color-aydin-red` #e10600, `-hover` #b80500, `-light` #ff2a1f for small red text on black, white, neutral greys, WhatsApp green). No cream, burgundy or orange anywhere; `warm-white`/`warm-cream` are kept as names but are both pure white. The home CSS reads those tokens (`--cine-*` only aliases them). Body font is Plus Jakarta Sans (`--font-body`), headings keep Roboto Slab (menu) / Bebas Neue (home).
- `src/lib/cinematic/effects.ts` is a separate lazy chunk started after the engine (SplitText headings, stagger-revealed menu cards, magnetic buttons on fine pointers, red progress bar). It never loads in static mode. The scene marquee is pure CSS.
- Static-poster mode (Save-Data, 2g/3g, `prefers-reduced-motion`) is chosen before paint by an inline script in `(home)/layout.tsx` that sets `data-mode="static"` on `#cine-root`; CSS in `(home)/cinematic.css` does the rest and the engine never loads.
